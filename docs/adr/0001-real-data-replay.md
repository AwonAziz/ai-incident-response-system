# 0001. Evaluate on real labelled telemetry, not the simulator

* Status: accepted
* Date: 2026-10-04

## Context

The pipeline was built and tested against a seeded telemetry simulator. That is
the right tool for testing plumbing - it can produce a degradation on demand, at
a known tick, deterministically - and 305 tests rely on it.

It cannot answer the question a reviewer will actually ask: *does this detection
approach work on telemetry it did not generate?* A simulator is generated by the
same assumptions as the detector, so any agreement between them is partly
circular. The first attempt at an "evaluation" made that explicit and useless:
labels came from the same `RuleEngine` the pipeline uses, so it measured internal
consistency, not effectiveness.

## Decision

Add a replay path for **real** telemetry with published ground truth, and run all
detectors through it on equal terms.

* Dataset: Numenta's Anomaly Benchmark (NAB), `realAWSCloudwatch` subset - 17
  real AWS CloudWatch series (EC2/RDS CPU utilisation, disk write bytes, network
  in, ELB request count), 62,049 points, 30 labelled anomaly windows.
* Fetched on demand by `scripts/fetch_nab_dataset.py`, pinned to a git ref, with a
  sha256 manifest so results cannot silently drift. Nothing is committed to the
  repository.
* `ReplayCollector` is a `BaseCollector` like the simulators, so real series flow
  through the same `Metric` construction, rolling window, feature engineering,
  rule evaluation and triage as production traffic.

## Consequences

* Real findings replace assumed ones. Three of them changed the code:
  * the configured `warn_high` thresholds do not transfer to real traffic (NAB
    CPU series are normalised to 0-1, so a 78% CPU threshold never fires);
  * the rolling-window length, not the choice of detector, dominated the
    IsolationForest's ranking quality (AUC 0.560 at 30 samples to 0.616 at 288);
  * the IsolationForest pages more false alarms on unseen normal data than a
    20-line EWMA control chart does.
* The simulator stays, because deterministic degradation is still the right tool
  for testing the incident lifecycle end to end.
* Extra moving parts: a download step, a second loader, an evaluation harness.
  The benchmark is opt-in (`scripts/benchmark.py`), never on the test path, so
  CI stays offline and fast.

## Revisit when

A second labelled dataset becomes available (SMD, SKAB, a proprietary export).
The harness takes a list of `LabelledSeries`, so adding one is a loader plus a
directory argument - the decision would only change if the new data showed the
current findings are dataset artefacts.
